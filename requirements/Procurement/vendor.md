# Requirement: ผู้ขาย (Vendor)

| | |
| --- | --- |
| Bounded Context | Procurement |
| สถานะ | เสร็จสิ้น |
| ผู้เขียน | ตัวอย่าง (เขียนย้อนหลังจาก feature ที่มีอยู่แล้ว) |
| วันที่เขียน | 2026-09-02 |
| Roadmap Phase (ถ้ามี) | Phase 2 pilot — feature แรกที่ใช้ครบทั้ง permission, concurrency test, functional test |

## 1. เป้าหมายและบริบท (Goal & Context)

ระบบจัดซื้อจัดจ้างต้องมีทะเบียนผู้ขาย/ผู้จำหน่าย (Vendor) กลางไว้ใช้อ้างอิงตอนสร้างสัญญา (Contract) — ก่อนหน้านี้ข้อมูลผู้ขายกระจายอยู่ในเอกสารแยกแต่ละแผนก ทำให้เวลาทำสัญญาใหม่ต้องมาถามซ้ำว่าที่อยู่/เลขผู้เสียภาษีของผู้ขายรายนี้คืออะไร และไม่มีที่เดียวที่แก้ไขข้อมูลแล้วอัปเดตทุกที่พร้อมกัน ผู้ใช้งานหลักคือเจ้าหน้าที่พัสดุ/จัดซื้อที่ต้องออกสัญญากับผู้ขาย

## 2. ขอบเขต (Scope)

### สิ่งที่ต้องทำในรอบนี้ (In scope)

- CRUD ข้อมูลผู้ขายพื้นฐาน (สร้าง/แก้ไข/ดู/ค้นหารายการ)
- ผูกสิทธิ์การเข้าถึงแบบ permission (`vendors.*`)

### สิ่งที่ไม่รวมในรอบนี้ (Out of scope)

- การผูกผู้ขายเข้ากับสัญญา (`ContractVendor`) — เป็น feature แยกต่างหาก
- ประวัติการเปลี่ยนแปลงราคา/เรตติ้งผู้ขาย — ยังไม่มีในระบบ
- การลบผู้ขายแบบถาวร (hard delete) — ใช้ `IsActive`/soft delete ผ่าน `EntityBase` ตามมาตรฐานทั้งระบบแทน

## 3. ศัพท์ที่เกี่ยวข้อง (Domain terms)

- **ผู้ขาย/ผู้จำหน่าย (Vendor)** — นิติบุคคลที่โรงพยาบาลทำสัญญาซื้อ/จ้างด้วย ตรงกับที่ใช้ใน [domain.md](../../.ai/domain.md)
- **รหัส SAP (SapCode)** — รหัสอ้างอิงผู้ขายในระบบ SAP ของโรงพยาบาล ใช้เป็นรหัสค้นหาแทนชื่อได้

## 4. ข้อมูล/ฟิลด์ที่เกี่ยวข้อง (Data / Fields)

| ชื่อฟิลด์ (ไทย) | ชื่อฟิลด์ (English) | ประเภทข้อมูล | บังคับ/ไม่บังคับ | กติกา/validation |
| --- | --- | --- | --- | --- |
| ชื่อบริษัทผู้ขาย/ผู้จำหน่าย | `Name` | ข้อความ | บังคับ | ห้ามว่าง |
| ชื่อบริษัทผู้ขาย (ภาษาอังกฤษ) | `NameEnglish` | ข้อความ | บังคับ | ห้ามว่าง |
| รหัส SAP | `SapCode` | ข้อความ | บังคับ | ห้ามว่าง |
| ที่อยู่ | `Address` | ข้อความ | บังคับ | ห้ามว่าง |
| จังหวัด | `ProvinceName` | ข้อความ | บังคับ | ห้ามว่าง |
| อำเภอ | `DistrictName` | ข้อความ | บังคับ | ห้ามว่าง |
| ตำบล | `SubDistrictName` | ข้อความ | บังคับ | ห้ามว่าง |

| เบอร์โทรศัพท์ | `Phone` | ข้อความ | บังคับ | ห้ามว่าง, ความยาวต้องเท่ากับ 10 หลักพอดี |
| เบอร์แฟกซ์ | `Fax` | ข้อความ | ไม่บังคับ | — |

## 5. ความสัมพันธ์กับข้อมูลอื่น (Relationships)

- ผู้ขาย 1 ราย อาจถูกผูกกับสัญญา (`Contract`) ได้หลายฉบับ ผ่าน `ContractVendor` (feature แยก ดูข้อ 2 "Out of scope")

## 6. กติกาทางธุรกิจ (Business Rules)

- รหัสไปรษณีย์และเบอร์โทรศัพท์ตรวจสอบเฉพาะ**ความยาว** ไม่ได้ตรวจรูปแบบ/checksum
- เลขผู้เสียภาษี (Tax) ไม่บังคับกรอก แต่ถ้ากรอกมาต้องยาว 13 หลักพอดี

## 7. ผลกระทบต่อเงิน/จำนวนคงเหลือ (Money & Quantity Impact)

- [ ] ใช่ แตะเงิน/จำนวนคงเหลือ
- [x] ไม่แตะเงิน/จำนวนคงเหลือ — ผู้ขายเป็นข้อมูลอ้างอิง (master data) ไม่มีฟิลด์เงิน/จำนวนในตัวเอง

## 8. สิทธิ์การเข้าถึง (Permissions)

- `vendors.view` — ดูรายการ/รายละเอียดผู้ขาย
- `vendors.create` — สร้างผู้ขายใหม่
- `vendors.update` — แก้ไขข้อมูลผู้ขาย

(เป็น feature แรกในระบบที่ใช้ permission convention นี้จริง — ดู [ai-agent-guide.md](../../.ai/ai-agent-guide.md))

## 9. หน้าจอที่เกี่ยวข้อง (UI / Frontend)

- `list` — ตารางรายชื่อผู้ขาย คอลัมน์: ชื่อผู้ขาย, รหัส SAP, จังหวัด, เบอร์โทร
- `create` / `edit` — ฟอร์มกรอกฟิลด์ตามข้อ 4 ทั้งหมด
- `view` — ดูรายละเอียดอย่างเดียว

## 10. เกณฑ์การยอมรับ (Acceptance Criteria)

- [ ] เมื่อกรอกข้อมูลผู้ขายครบและถูกต้องแล้วกด "บันทึก" ระบบควรจะสร้างผู้ขายใหม่สำเร็จและแสดงในหน้ารายการ
- [ ] เมื่อเว้นฟิลด์บังคับว่าง (เช่น ชื่อ) แล้วกด "บันทึก" ระบบควรจะไม่บันทึกและแจ้งข้อความ validation ที่ field นั้น
- [ ] เมื่อกรอกรหัสไปรษณีย์ไม่ครบ 5 หลัก ระบบควรจะแจ้ง error และไม่บันทึก
- [ ] เมื่อผู้ใช้ไม่มีสิทธิ์ `vendors.create` แล้วพยายามสร้างผู้ขายใหม่ ระบบควรจะปฏิเสธคำขอ

## 11. เคสที่ต้องทดสอบ (Test Cases)

### กรณีสำเร็จ (Happy path)

- สร้างผู้ขายด้วยข้อมูลครบถ้วนถูกต้อง (รวมกรอก Tax 13 หลัก) → สำเร็จ
- สร้างผู้ขายโดยไม่กรอก Fax/Email/Tax (ฟิลด์ไม่บังคับ) → สำเร็จ

### กรณีข้อมูลไม่ถูกต้อง (Validation)

- ไม่กรอก Name / NameEnglish / SapCode / Address / ProvinceName / DistrictName / SubDistrictName / Phone → validation fail ทีละฟิลด์
- PostalCode ยาวไม่เท่ากับ 5 หลัก → validation fail
- Phone ยาวไม่เท่ากับ 10 หลัก → validation fail
- กรอก Tax แต่ยาวไม่เท่ากับ 13 หลัก → validation fail

### กรณีอื่น ๆ

- แก้ไขผู้ขายเดียวกันพร้อมกันสองคน (concurrency) → คนที่บันทึกทีหลังต้องได้ error แทนที่จะเขียนทับข้อมูลของอีกคนเงียบ ๆ (มี functional test จริงอยู่แล้วที่ `tests/Application.FunctionalTests` — `VendorUpdateCommandTests`)
