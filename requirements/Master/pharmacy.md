## 1. เป้าหมายและบริบท (Goal & Context)

สมาคมเภสัชกรรมชุมชนต้องมีทะเบียนร้านขายยา (Pharmacy) เป็นข้อมูลหลักของระบบ — ร้านขายยาคือผู้ใช้งานหลักที่บันทึกข้อมูลและให้บริการแก่ผู้รับบริการ ก่อนมีทะเบียนกลาง รหัสร้าน ชื่อร้าน ที่ตั้ง ใบอนุญาต และช่องทางติดต่อจะไม่มีที่อ้างอิงเดียว ทำให้ผูกผู้ใช้ (User) และเภสัชกร (Pharmacist) เข้ากับร้านไม่ได้ ผู้ใช้งานหลักคือเจ้าหน้าที่สมาคมที่ดูแลข้อมูลสมาชิก/ร้านยา และผู้ใช้ของร้านที่ต้องเห็นข้อมูลร้านของตนเอง

ถ้าไม่มี feature นี้ ระบบจะมีแค่คลาสใน Domain แต่ยังสร้าง แก้ไข ค้นหา หรือปิดการใช้งานร้านยาผ่านหน้าจอไม่ได้

## 2. ขอบเขต (Scope)

### สิ่งที่ต้องทำในรอบนี้ (In scope)

- CRUD ข้อมูลร้านขายยาพื้นฐาน (สร้าง/แก้ไข/ดู/ค้นหารายการ) ตามฟิลด์ใน `Pharmacy`
- เลือกกลุ่มร้านยา (`PharmacyGroup`) และประเภทร้านยา (`PharmacyType`) จากข้อมูลตั้งต้นที่มีอยู่แล้ว
- เลือกจังหวัด / อำเภอ / ตำบล จากข้อมูลที่อยู่ที่มีอยู่แล้ว
- ผูกสิทธิ์การเข้าถึงแบบ permission (`pharmacies.*`) — ยังไม่มีในระบบ ต้องสร้างใหม่
- ปิดการใช้งานร้านยาผ่าน `IsActive` / `DeleteFlag` ของ `BaseEntity` (soft delete) ไม่ลบแถวทิ้ง

### สิ่งที่ไม่รวมในรอบนี้ (Out of scope)

- ข้อมูลบัญชีธนาคาร — ฟิลด์ `AccNo`, `AccName`, `BankID`, `BankBrunch`, `BankType` ถูกคอมเมนต์ไว้ใน entity แล้ว ยังไม่ทำ
- CRUD กลุ่มร้านยา (`PharmacyGroup`) และประเภทร้านยา (`PharmacyType`) — มีตัว initializer ฝังข้อมูลตั้งต้นอยู่แล้ว เป็น feature แยก
- CRUD เภสัชกร (`Pharmacist`) และการจัดการผู้ใช้ (`User`) — อ้างอิงร้านยาจาก feature นี้ แต่ไม่สร้าง/แก้ในรอบนี้
- ผู้ป่วย (`Patient`) และรายการให้บริการ (`Service`)
- การลบร้านยาแบบถาวร (hard delete)

## 3. ศัพท์ที่เกี่ยวข้อง (Domain terms)

- **ร้านขายยา (Pharmacy)** — ข้อมูลร้านขายยาซึ่งเป็นผู้ใช้งานระบบหลัก ประกอบด้วยรหัส ชื่อร้าน ที่ตั้ง ตรงกับ [domain.md](../../.ai/domain.md)
- **กลุ่มร้านยา (PharmacyGroup)** — กลุ่มที่ร้านสังกัด เช่น ร้านยาเดี่ยว, ร้านยาเครือข่าย, โรงพยาบาล มีรหัสและชื่อของตัวเอง
- **ประเภทร้านยา (PharmacyType)** — ประเภทของหน่วยบริการ เช่น ร้านยาเดี่ยว, ร้านยา GPP, ร้านยาเภสัชกร, โรงพยาบาล, รพสต., เภสัชกร, อื่นๆ
- **รหัส สปสช. (NhsoCode)** — รหัสหน่วยบริการของสำนักงานหลักประกันสุขภาพแห่งชาติ
- **จังหวัดตาม อย. (Fda_Province)** — จังหวัดที่ใช้กับสำนักงานคณะกรรมการอาหารและยา เก็บเป็นข้อความแยกจากจังหวัดของที่อยู่
- **ผู้ประสานงาน (Co_Name / Co_Mail / Co_Tel)** — คนติดต่อของร้าน แยกจากเบอร์และอีเมลสำนักงาน

กลุ่มร้านยาที่ seed ไว้แล้ว: A ร้านยาเดี่ยว, B ร้านยา Boots, C ร้านยาเครือข่ายร้อยแก่นสารสินธุ์, H โรงพยาบาล, P ร้านยา Pure (Big C), W ร้านยา Watsons, X ร้านยา Xta (CP)

ประเภทร้านยาที่ seed ไว้แล้ว: 1 ร้านยาเดี่ยว, 2 ร้านยา GPP, 3 ร้านยาเภสัชกร, 4 โรงพยาบาล, 5 รพสต., 6 เภสัชกร, 7 อื่นๆ

## 5. ความสัมพันธ์กับข้อมูลอื่น (Relationships)

- ร้านขายยา 1 ร้าน อยู่ได้ 1 กลุ่มร้านยา (`PharmacyGroup`) และ 1 ประเภทร้านยา (`PharmacyType`) ความสัมพันธ์เป็น optional
- ร้านขายยา 1 ร้าน ชี้ไปจังหวัด (`Province`) อำเภอ (`District`) ตำบล (`SubDistrict`) ได้อย่างละ 1 รายการ ความสัมพันธ์เป็น optional
- อำเภอต้องสังกัดจังหวัด และตำบลต้องสังกัดอำเภอ ตาม master ที่อยู่ที่มีอยู่แล้ว
- เภสัชกร (`Pharmacist`) หลายคนอ้างอิงร้านขายยาเดียวกันผ่าน `PharmacyId`
- ผู้ใช้ (`User`) ผูกกับร้านขายยา 1 ร้านผ่าน `PharmacyId` (บังคับที่ฝั่ง User)

## 6. กติกาทางธุรกิจ (Business Rules)

- รหัสร้านยา (`Code`) และชื่อร้านยา (`Name`) ห้ามว่าง — เป็นสองค่าที่ constructor ของ entity รับ
- ฟิลด์ที่เหลือไม่บังคับกรอก รวมถึงที่อยู่ ช่องทางติดต่อ และพิกัด
- เมื่อเลือกประเภทร้านยาเป็น "อื่นๆ" (รหัส `7` ในข้อมูลตั้งต้น) ให้กรอก `PharmacyTypeOther` ได้ — ยังไม่ถูกบังคับใน entity ต้องคุยกับทีมก่อนว่าจะบังคับหรือไม่
- ถ้าเลือกทั้งจังหวัดและอำเภอ อำเภอต้องอยู่ภายใต้จังหวัดนั้น ถ้าเลือกทั้งอำเภอและตำบล ตำบลต้องอยู่ภายใต้อำเภอนั้น
- ไม่ลบร้านยาทิ้ง ใช้ `IsActive` / `DeleteFlag` ตาม `BaseEntity`
- รหัสร้านยาซ้ำได้หรือไม่ และรูปแบบอีเมล/เบอร์โทร/รหัสไปรษณีย์ — ไม่แน่ใจ ต้องคุยกับทีมก่อน โค้ดปัจจุบันยังไม่ตรวจ

## 8. สิทธิ์การเข้าถึง (Permissions)

ยังไม่มี permission ของร้านยาในระบบ ต้องสร้างใหม่ตามรูปแบบ `module.action` (ดู [coding-rules.md](../../.ai/coding-rules.md)):

- `pharmacies.view` — ดูรายการ/รายละเอียดร้านขายยา
- `pharmacies.create` — สร้างร้านขายยาใหม่
- `pharmacies.update` — แก้ไขข้อมูลร้านขายยา

## 9. หน้าจอที่เกี่ยวข้อง (UI / Frontend)

- `list` — ตารางรายชื่อร้านขายยา คอลัมน์: รหัสร้านยา, ชื่อร้านยา, เลขที่ใบอนุญาต, กลุ่มร้านยา, จังหวัด, เบอร์โทรสำนักงาน
- `create` / `edit` — ฟอร์มกรอกฟิลด์ตามข้อ 4 ทั้งหมด
- `view` — ดูรายละเอียดอย่างเดียว
- dropdown / lookup:
  - กลุ่มร้านยา จาก `PharmacyGroup`
  - ประเภทร้านยา จาก `PharmacyType` เมื่อเลือก "อื่นๆ" ให้แสดงช่อง `PharmacyTypeOther`
  - จังหวัด แล้วกรองอำเภอตามจังหวัด แล้วกรองตำบลตามอำเภอ

## 10. เกณฑ์การยอมรับ (Acceptance Criteria)

- [ ] เมื่อกรอกรหัสร้านยาและชื่อร้านยาครบแล้วกด "บันทึก" ระบบควรจะสร้างร้านขายยาใหม่สำเร็จและแสดงในหน้ารายการ
- [ ] เมื่อสร้างร้านโดยกรอกเฉพาะรหัสกับชื่อ (ฟิลด์อื่นเว้นว่าง) ระบบควรจะบันทึกสำเร็จ
- [ ] เมื่อเว้นรหัสร้านยาหรือชื่อร้านยาแล้วกด "บันทึก" ระบบควรจะไม่บันทึกและแจ้ง validation ที่ฟิลด์นั้น
- [ ] เมื่อเลือกกลุ่มร้านยา ประเภทร้านยา จังหวัด อำเภอ และตำบลที่มีอยู่จริง ระบบควรจะบันทึกความสัมพันธ์นั้นและแสดงชื่อที่เลือกในหน้ารายละเอียด
- [ ] เมื่อเลือกอำเภอที่ไม่อยู่ภายใต้จังหวัดที่เลือก ระบบควรจะไม่บันทึกและแจ้งว่าที่อยู่ไม่สัมพันธ์กัน
- [ ] เมื่อผู้ใช้ไม่มีสิทธิ์ `pharmacies.create` แล้วพยายามสร้างร้านขายยา ระบบควรจะปฏิเสธคำขอ
- [ ] เมื่อปิดการใช้งานร้านยา ระบบควรจะไม่ลบแถว และรายการที่ถูกปิดไม่โผล่ในหน้ารายการที่แสดงเฉพาะร้านที่ใช้งานอยู่

## 11. เคสที่ต้องทดสอบ (Test Cases)

### กรณีสำเร็จ (Happy path)

- สร้างร้านขายยาด้วยรหัสและชื่อเท่านั้น → สำเร็จ
- สร้างร้านขายยากรอกฟิลด์ครบ รวมกลุ่มร้านยา ประเภทร้านยา ที่อยู่ครบสายจังหวัด-อำเภอ-ตำบล และช่องทางติดต่อ → สำเร็จ
- แก้ไขชื่อร้าน เบอร์โทร และพิกัดของร้านที่มีอยู่ → สำเร็จ และค่าเดิมที่ไม่ได้แก้ยังอยู่

### กรณีข้อมูลไม่ถูกต้อง (Validation)

- ไม่กรอก `Code` → validation fail
- ไม่กรอก `Name` → validation fail
- เลือก `PharmacyGroup` / `PharmacyType` / `Province` / `District` / `SubDistrict` ที่ไม่มีในระบบ → validation fail
- เลือกอำเภอคนละจังหวัดกับจังหวัดที่เลือก หรือตำบลคนละอำเภอกับอำเภอที่เลือก → validation fail

### กรณีอื่น ๆ (ไม่พบข้อมูล, แก้ไขพร้อมกันสองคน, สิทธิ์ไม่พอ ฯลฯ)

- เปิดรายละเอียดร้านยาที่ไม่มีอยู่ → ไม่พบข้อมูล
- แก้ไขร้านยาเดียวกันพร้อมกันสองคน → คนที่บันทึกทีหลังต้องได้ error แทนที่จะเขียนทับข้อมูลของอีกคนเงียบ ๆ
- ผู้ใช้ไม่มี `pharmacies.view` / `pharmacies.create` / `pharmacies.update` → ปฏิเสธคำขอตาม action นั้น
- ปิดการใช้งาน (`IsActive` / `DeleteFlag`) แล้วร้านยังถูกอ้างอิงโดย `User` หรือ `Pharmacist` ได้ — ไม่ลบแถวร้านทิ้ง

## 14. บันทึกเพิ่มเติมสำหรับ AI (ไม่บังคับ)

- ทำโครง CRUD, permission และหน้า `list` / `create` / `edit` / `view` ตามโครงสร้าง feature มาตรฐานใน [.ai/architecture.md](../../.ai/architecture.md)
- ฟิลด์บัญชีธนาคารที่ถูกคอมเมนต์ใน `Pharmacy.cs` ห้ามนำกลับมาในรอบนี้
- ใน entity ตอนนี้ `PharmacyGroupId` และ `PharmacyTypeId` เป็น `string?` แต่คีย์ของ `PharmacyGroup` / `PharmacyType` เป็น `int` ของ `BaseEntity` — migration จึงเกิด shadow FK `PharmacyGroupId1` และ `PharmacyTypeId1` ก่อน implement ให้จัดความสัมพันธ์นี้ให้ชี้ไปที่คีย์จริงของกลุ่มและประเภท อย่าเพิ่มคอลัมน์ FK ซ้ำอีกชุด
- `Province` / `District` / `SubDistrict` ใช้ `string Id` อยู่แล้ว สัมพันธ์กับ `ProvinceId` / `DistrictId` / `SubDistrictId` ได้ตรง
- รูปแบบอีเมล เบอร์โทร รหัสไปรษณีย์ และความไม่ซ้ำของ `Code` ยังไม่กำหนดในโค้ด อย่าใส่ validation เหล่านี้จนกว่าทีมจะยืนยัน
