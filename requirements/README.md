# Requirements

โฟลเดอร์นี้เก็บ **requirement ของแต่ละ feature** ในโปรเจกต์นี้ — เขียนโดยทีม (ไม่จำเป็นต้องเป็นโปรแกรมเมอร์) เป็นภาษาไทย ตามโครงสร้างเดียวกันทุกไฟล์ แล้วใช้เป็นบริบทให้ทั้ง **คน** (เข้าใจว่าต้องทำอะไร) และ **AI** (เช่น Claude Code — ใช้ implement/เขียนเทส) อ่านชุดเดียวกัน

> ทำไมต้องมีโฟลเดอร์นี้: โปรเจกต์นี้จะใช้ AI เป็นหลักในการพัฒนา/เขียนเทส — AI ทำงานได้ดีแค่ไหนขึ้นกับว่าได้รับบริบทชัดเจนแค่ไหน ถ้า requirement กระจัดกระจายอยู่ในแชท/ปาก ทุกครั้งที่เริ่ม session ใหม่ต้องอธิบายใหม่หมด และรายละเอียดอาจตกหล่นหรือขัดกันเองระหว่างรอบ การเขียน requirement เป็นไฟล์ที่มีโครงสร้างชัดเจนไว้ล่วงหน้า ช่วยทั้งคนที่มาทำงานต่อและ AI ที่ไม่เคยเห็นบริบทมาก่อนเลย

## ใครเขียน

ใครก็ได้ที่รู้ว่า feature นี้ต้องทำอะไร — เจ้าของ feature, ทีมธุรกิจ/จัดซื้อ, หรือโปรแกรมเมอร์เองก็ได้ **ไม่จำเป็นต้องเขียนโค้ดเป็น** แต่ควรตอบคำถามในเทมเพลตให้ครบและชัดเจนที่สุดเท่าที่ทำได้ ส่วนไหนไม่รู้/ไม่แน่ใจให้เขียนว่า "ไม่แน่ใจ — ต้องคุยกับทีมก่อน" แทนการเดา

## เริ่มเขียน requirement ใหม่

1. คัดลอกไฟล์ [`_template.md`](_template.md)
2. เอาไปวางในโฟลเดอร์ย่อยตาม **bounded context** ที่ feature นี้เกี่ยวข้อง (ดูความหมายแต่ละ context ที่ [architecture.md](../.ai/architecture.md) หัวข้อ "Bounded-context folder map"):

   - `ReferenceData/` — อาคาร, ชั้น, ห้อง/สถานที่, แผนก, กอง, กลุ่มบริการ, จังหวัด/อำเภอ/ตำบล, หน่วยนับ
   - `Catalog/` — รายการสินค้า/ครุภัณฑ์ (Item)
   - `Contracts/` — สัญญา, ประเภทสัญญา, หลักประกันสัญญา, คณะกรรมการตรวจรับ
   - `Procurement/` — ผู้ขาย, ราคาอ้างอิง, และในอนาคต แผนจัดซื้อ/ใบขอซื้อ/ใบสั่งซื้อ/ใบรับของ
   - `Security/` — สิทธิ์การเข้าถึง (permission/role)
   - `Inventory/` — คลังสินค้า, ยอดคงคลัง, การเคลื่อนไหวสต๊อก

   ถ้าไม่แน่ใจว่าอยู่ context ไหน หรือ feature คาบเกี่ยวหลาย context ให้ถามทีม หรือเขียนเหตุผลไว้ในไฟล์แล้วเลือก context หลักที่เกี่ยวข้องมากที่สุด

3. ตั้งชื่อไฟล์เป็นภาษาอังกฤษ kebab-case สื่อความหมาย เช่น `vendor.md`, `contract-renewal-reminder.md` (ไม่ต้องใส่เลขลำดับนำหน้า — ประวัติการแก้ไขดูจาก Git ได้อยู่แล้ว)
4. กรอกทุกหัวข้อในเทมเพลตให้ครบที่สุดเท่าที่ทำได้ — แต่ละหัวข้อมีคำแนะนำ (บรรทัดที่ขึ้นต้นด้วย `>`) กำกับไว้ว่าต้องตอบอะไร
5. commit ไฟล์นี้เข้า branch เหมือนโค้ดทั่วไป (ดูขั้นตอน Git ที่ [dev-workflow.md](../.ai/dev-workflow.md) ส่วนที่ 9)

ดูตัวอย่างไฟล์ที่กรอกแล้วจริงได้ที่ [`Procurement/vendor.md`](Procurement/vendor.md) (สร้างย้อนหลังจาก feature ที่มีอยู่แล้วในระบบ เพื่อให้เห็นว่าเทมเพลตกรอกแล้วหน้าตาเป็นอย่างไร)

## สถานะของ requirement

ระบุไว้ในตารางหัวไฟล์ (แถว "สถานะ") — อัปเดตเองเมื่อสถานะเปลี่ยน ไม่ต้องรอให้ใครมาสั่ง:

| สถานะ | ความหมาย |
| --- | --- |
| ร่าง | ยังเขียนไม่ครบ หรือยังต้องคุยรายละเอียดกับทีมก่อน — **ยังไม่พร้อมส่งให้ AI/dev เริ่มทำ** |
| พร้อมพัฒนา | กรอกครบ ทีมเห็นตรงกันแล้ว พร้อมเอาไปเริ่ม implement |
| กำลังพัฒนา | มีคนเริ่มทำแล้ว (คน หรือ AI) |
| เสร็จสิ้น | พัฒนา + เทสผ่านตามเกณฑ์การยอมรับในไฟล์แล้ว |

## ใช้ร่วมกับ AI ยังไง

เมื่อ requirement สถานะ "พร้อมพัฒนา" แล้ว ให้ทำตาม [prompt-templates.md](../.ai/prompt-templates.md):

1. วาง **shared preamble** (บริบทมาตรฐานของโปรเจกต์) ก่อนเสมอ
2. วาง prompt template ของสเตจที่จะทำ (Domain entity, CQRS feature, unit test, functional test, frontend, e2e — เลือกตามที่ต้องการ)
3. ในช่อง `Requirement: {fill in}` ท้าย template นั้น ให้ใส่ **path ของไฟล์ requirement** (เช่น `requirements/Procurement/vendor.md`) หรือ copy เนื้อหาทั้งไฟล์วางไปเลยก็ได้ — AI agent จะอ่านไฟล์นั้นเป็นบริบทหลักในการ implement
4. **ให้ AI เสนอแผนก่อน อย่าเพิ่งให้แก้โค้ดทันที** — บอก AI ว่ายังไม่ต้องแก้ไฟล์จริง ขอดูแผนก่อน (Claude Code สั่งเข้า Plan Mode ได้โดยตรง) ทีมอ่านแผน ปรับแก้ถ้าเข้าใจ requirement ผิด แล้วค่อยให้เริ่มลงมือทำจริง — ดูรายละเอียดที่ [dev-workflow.md](../.ai/dev-workflow.md) ส่วนที่ 3.2

requirement หนึ่งไฟล์มักจะต้องใช้หลาย prompt template ทำต่อกันหลายรอบ (Domain entity → CQRS feature → unit test → functional test → frontend) — ใช้ requirement ไฟล์เดิมซ้ำได้ทุกรอบ ไม่ต้องเขียนใหม่
