### `EntityBase` redesign: real soft-delete + scoped `IsActive`, informed by `cwie` (2026-08-21)

Requested directly: analyze what `IsDelete`/`IsActive` should be for an ERP/inventory system, informed by the sibling `cwie` reference project, and propose + implement a plan (planned via `EnterPlanMode`/`ExitPlanMode`, approved before implementation — see the session's plan file for the full design writeup). Motivated by real bugs this session had already hit from the lack of structure: `UpdateServiceGroupCommandValidator` blocking every deactivation, `ServiceGroupsController` missing its `{id}` route, and (found during this redesign's own research) `ContractVendorsCommandHandler` hardcoding `IsActive = true; IsDelete = false;` on every update, plus the fact that only 4 of 36 `Get*Query` handlers filtered soft-deleted rows at all before this change.

**Design** (adapted from `cwie`'s `BaseEntity`/`BaseAuditableEntity` split, corrected for a real difference: SUTH's audit interceptor stamps `CreatedBy`/`CreatedOn`/`LastModified`/`LastModifiedBy` on every entity including the ledger/security ones, so a literal port of cwie's zero-audit-fields base would have stripped audit columns from `StockMovement`/`StockItem`/`Permission`/`RolePermission` — a regression, not a cleanup):

- [x] `EntityBase` (`src/Domain/Common/EntityBase.cs`) — `IsDelete`/`IsActive` removed; every entity keeps its audit fields (`CreatedBy`/`CreatedOn`/`LastModifiedBy`/`LastModified`) unchanged.
- [x] New `SoftDeletableEntityBase : EntityBase` (`src/Domain/Common/SoftDeletableEntityBase.cs`) — `IsDeleted` (renamed from `IsDelete` — correct past-participle grammar, disambiguates from the new fields), `DeletedOn`/`DeletedBy` (both nullable, only populated once deleted), and a real `MarkAsDeleted(string deletedBy)` behavior method (idempotent — a second call doesn't clobber the original `DeletedOn`/`DeletedBy`) replacing raw `entity.IsDelete = true` mutation scattered across handlers.
- [x] New `IHasActiveFlag` marker interface (`src/Domain/Common/IHasActiveFlag.cs`) — `IsActive` is no longer on every entity; it's declared per-entity only where domain-meaningful (matches `cwie`'s own precedent of declaring it directly on entities like `Province`, not on a shared base).
- [x] **Global EF Core query filter** (`InventoryDbContext.OnModelCreating`, reflection over every `SoftDeletableEntityBase`-derived type, cwie's exact pattern) — `HasQueryFilter(e => !e.IsDeleted)` applied automatically to all 21 soft-deletable entities. This is the single highest-value fix: it structurally eliminates the "forgot to filter deleted rows" bug class at the source (32 of 36 query handlers had this gap before) instead of requiring every future handler to remember it by hand. Verified live: a soft-deleted row is invisible to a plain query with *zero* manual filtering, and still provably present via `.IgnoreQueryFilters()` (soft-delete, not a hard delete).
- [x] `EntityBaseConfigurationExtensions` split into three composable extensions: `ConfigureEntityBase<T>()` (audit + dual-key + `xmin`, unchanged scope), new `ConfigureSoftDelete<T>()`, new `ConfigureActiveFlag<T>()` — directly prevents a repeat of the earlier `SubDistrictConfiguration`-missing-audit-config bug for the new flags.
- [x] `AuditableEntitySaveChangesInterceptors`: removed the unconditional `entry.Entity.IsActive = true; entry.Entity.IsDelete = false;` on every `Added` entity (it has nothing generic left to act on now) — this was silently forcing every Create command's `StatusFlag` input to `true` regardless of what was requested; **`CreateDepartmentCommand.StatusFlag` (previously flagged as a dead parameter) now actually takes effect, for free.** Also added detection so a soft-delete (`Modified` entry whose `IsDeleted` flips `false`→`true`) logs `AuditAction.Deleted` instead of `AuditAction.Updated` — previously `AuditAction.Deleted` was dead code (only fired for a real `DbSet.Remove()`, which nothing calls on a soft-deletable entity). Verified live: the `AuditLog` row for a soft-delete now genuinely has `Action = Deleted`.
- [x] **Per-entity decisions** (all 25 entities): **18** get both soft-delete and `IsActive` (the entities that already had working `StatusFlag`↔`IsActive` mappings, plus `Item`, added proactively before any CRUD exists for it, since "discontinued but still referenced by history" is exactly the pattern already proven for `UnitOfMeasure`). **2** (`Contract`, `ContractCommittee`) get soft-delete only, no `IsActive` yet. **5** stay on plain `EntityBase` — no soft-delete, no `IsActive`: `RolePermission` and `ContractVendor` (both binary participation/grant links — a role either has a permission or doesn't, a vendor either participates in a contract or doesn't; `RolePermission` in particular sits in `AuthorizationBehaviour`'s hot path, making it the single worst entity in the codebase to leave soft-deletable), `Permission` (seed-only catalog, no real usage), and `StockMovement`/`StockItem` (the append-only ledger and its materialized projection — a soft-deletable `StockItem` could vanish from queries while its `StockMovement` rows still exist, silently breaking the `QuantityOnHand == SUM(StockMovement.Quantity)` invariant; excluding both is the non-negotiable "append-only ledger" rule enforced at the type level instead of by convention).
- [x] Fixed `ContractVendorsCommandHandler`'s hardcoded `IsActive = true; IsDelete = false;` as a direct consequence — those fields no longer exist on `ContractVendor`, so the handler was rewritten to just update `ContractId`/`VendorId` (also removed a stray unused `using static System.Runtime.InteropServices.JavaScript.JSType;` import and a redundant post-constructor re-set of the same two fields in `CreateContractVendorsCommand`, same class of copy-paste damage already fixed elsewhere this session).
- [x] `DeleteUnitOfMeasureCommand`/`DeleteServiceGroupCommand` updated to call `entity.MarkAsDeleted(currentUser)` instead of raw property mutation; their manual `!x.IsDeleted` filters removed from `GetUnitOfMeasure(s)Query`/`GetServiceGroup(s)Query` (the global filter now does that for free — removing the manual filter and confirming soft-deleted rows still don't leak through was itself the smoke test that the global filter is wired correctly).
- [x] Migration regenerated per the project's established "migrations are disposable during this phase" convention (dev DB dropped, fresh `InitialCreate`, `dotnet ef database update`) — verified via `psql` that the resulting schema exactly matches the design across all three categories (`unit_of_measures` has `is_active`+`is_deleted`/`deleted_on`/`deleted_by`; `contracts` has only the soft-delete columns; `role_permissions`/`stock_movements`/`contract_vendors` have neither).
- [x] Full verification: `dotnet build` clean (0 errors — only 2 pre-existing `Domain.UnitTests` compile errors from `BuildingTests.cs` referencing the old property names, fixed); `dotnet test` 43/43 passing including the Vendor optimistic-concurrency (`xmin`) test, confirming the `ConfigureEntityBase` split didn't disturb the concurrency token; a live scratch-console smoke test proving all four behavioral changes above (global filter, soft-vs-hard-delete distinction, `AuditAction.Deleted`, the `CreateDepartmentCommand` bonus fix) against real Postgres; frontend `eslint`/`vite build` both clean (the `DeleteFlag`/`StatusFlag` JSON field names sent to the browser are unaffected — only the C# source property name each maps *from* changed).
- [x] Surfaced (not fixed — see Open above) a real EF Core model warning: `Contract`/`Item` are soft-deletable and are the required end of relationships with entities that are deliberately not (`ContractVendor`, `StockItem`/`StockMovement`) — currently harmless since neither has a working Delete command yet, but needs the "referenced by active child" guard (not a matching query filter — that would wrongly make the ledger soft-deletable) before either gets one.

### `FluentAssertions` replaced with `Shouldly` across all test projects (2026-08-19)

Running `dotnet test` printed an Xceed licensing notice: `FluentAssertions` 8.x+ is commercially licensed (Xceed acquired the project and changed the license starting at v8) — free only for non-commercial use, and this is a hospital system. Matched the `cwie` reference project's own choice (already on `Shouldly` 4.3.0 across all its test projects) rather than pinning back to FluentAssertions 7.x, since Shouldly is BSD-3 licensed with no commercial-use restriction at all, avoiding the risk of licensing changing out from under the project again.

- [x] `Directory.Packages.props`: `FluentAssertions` → `Shouldly 4.3.0`; all three test `.csproj` files updated to match.
- [x] `global using Shouldly;` added to each test project (`Domain.UnitTests`, `Application.FunctionalTests` — both already had a `GlobalUsings.cs`; `Application.UnitTests` didn't, so one was added) — removed the now-redundant per-file `using FluentAssertions;` from the ~24 files that had it (several had it BOM-prefixed on line 1, which a naive `sed` pass missed at first — caught and fixed).
- [x] Mechanically converted every `.Should().X()` call to Shouldly's equivalent across all three test projects (~190 call sites): `.Be`/`.NotBe`/`.BeTrue`/`.BeFalse`/`.BeNull`/`.NotBeNull`/`.Contain` all map 1:1 to `.ShouldBe`/`.ShouldNotBe`/etc. Three call shapes needed real (not just mechanical) translation, each verified against Shouldly's actual API via reflection on the installed assembly rather than assumed:
  - `collection.Should().HaveCount(0)` → `collection.ShouldBeEmpty()` (2 sites).
  - `collection.Should().BeEquivalentTo(expected)` → `collection.ShouldBe(expected, ignoreOrder: true)` (6 sites, all in `ValidationExceptionTests.cs`) — confirmed these tests genuinely depend on FluentAssertions' order-independent equivalence (the expected arrays are listed in a different order than insertion order on purpose), so a plain `.ShouldBe(expected)` would have been wrong (Shouldly's default sequence comparison is order-sensitive) — `ignoreOrder: true` was needed to preserve the original semantics exactly.
  - `await act.Should().ThrowAsync<T>()` → `await Should.ThrowAsync<T>(act)` (3 sites, `Application.FunctionalTests/Vendors/`) — Shouldly's async-throw assertion is a static method taking the delegate, not a fluent extension on it.
- [x] Verified with the actual concern in mind, not just passing tests: re-ran `dotnet test suth-inventory.sln` and confirmed the Xceed warning is gone entirely, and grepped the whole repo (excluding `obj`/`bin`) for any remaining `FluentAssertions` reference — none found.
- [x] All 43 tests still pass (21 Domain.UnitTests + 17 Application.UnitTests + 5 Application.FunctionalTests) — same counts as before the swap, confirming no test's assertion was accidentally weakened or dropped during the mechanical conversion.

### `ServiceGroups` CRUD rebuilt as the second Phase 3 reference feature (2026-08-19)

Requested as the natural next pick after `unit-of-measures` (already had dedicated routes; needed the shared-form-component + delete + e2e pieces to reach parity). Investigating the existing code before touching it surfaced that **ServiceGroup editing was completely non-functional**, via three independent, compounding bugs — worth reading in full since none of them would have been caught by a build or by the existing (zero) test coverage:

- [x] **`ServiceGroupsController`'s `[HttpPut(Name = "UpdateServiceGroup")]` had no `{id}` route segment** (`PUT /service-groups`, id only in the body), but the frontend edit page called `PUT /service-groups/{id}` — every save request 404'd before ever reaching the handler. Fixed by adding `[HttpPut("{id}")]` plus the `id != command.Id → BadRequest()` guard already used by `UnitOfMeasuresController`/`VendorsController`.
- [x] **`UpdateServiceGroupCommandValidator` had `RuleFor(p => p.StatusFlag).NotEmpty()` on a plain `bool`.** FluentValidation's `NotEmpty()` on a bool requires it to equal `true` (the type's non-default value) — so this validator rejected every attempt to set `StatusFlag = false`, meaning a ServiceGroup could never be deactivated even if the route bug above were fixed. ### `pnpm update --latest` incident (2026-08-17)
- [x] A blanket `pnpm store prune` + `pnpm update --latest` + `pnpm install` jumped ~60 packages across major versions at once (ESLint 8→10, Vite 6→8, Vuetify 3→4, Vue Router 4→5, Pinia, Tiptap 2→3, etc.) and broke the build (`@iconify/tools`'s new major dropped CommonJS `exports`, breaking the `postinstall` icon-build script). Given the blast radius, reverted `package.json`/`pnpm-lock.yaml` to the last committed baseline and reapplied only the specific, verified version bumps from the Phase 1 pass (`apexcharts@4.1.0`, `video.js@7.21.7`, `vite-plugin-vue-devtools@8.2.1`, `vite-plugin-vuetify@2.1.3`, `@playwright/test@1.62.1`) rather than accepting the full jump. **Lesson: don't run `pnpm update --latest` across the whole tree at once on this project** — use `pnpm outdated` / `pnpm update --interactive` and upgrade in small, testable batches instead, especially for Vite/Vuetify/ESLint/Vue Router, which this Vuexy-template frontend is structurally sensitive to.
- [x] Surfaced two previously-latent problems while recovering from the above (**both apply regardless of the incident** — worth knowing before the next real dependency upgrade):
  - `flatpickr` was only a *transitive* dependency (via `vue-flatpickr-component`); `AppDateTimePicker.vue`'s `@use "flatpickr/dist/flatpickr.css"` needs it resolvable at the top-level `node_modules`, which pnpm's default (non-flat) install doesn't guarantee even with `shamefully-hoist=true` in `.npmrc`, breaking `vite build`'s Sass compilation. Fixed by adding `flatpickr` as a direct `dependency` in `package.json` — the correct fix regardless of hoisting settings, since the code imports from it directly.
  - `pnpm-workspace.yaml`'s `ignoredBuiltDependencies` list (pre-existing, correct) triggers pnpm 11's newer build-script-approval prompt on `pnpm install`/`pnpm run *`; run non-interactively (no TTY), pnpm wrote an invalid placeholder `allowBuilds` block (`'@scarf/scarf': set this to true or false`, literally) instead of real booleans, which then hard-failed every subsequent `pnpm run` via its auto-triggered deps-status-check. Fixed by writing explicit `false` values for all six packages under `allowBuilds` in `pnpm-workspace.yaml` (matching the existing `ignoredBuiltDependencies` intent — none of them need their install scripts to run). **If `pnpm install` ever regenerates that block with placeholder text again, replace it with explicit `true`/`false` per package — don't leave the placeholder text, and don't run `pnpm approve-builds` interactively without checking what it writes.**
