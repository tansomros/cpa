API Convention คือข้อตกลงร่วมกันในการออกแบบ API เพื่อให้ระบบต่าง ๆ สื่อสารกันได้อย่างเป็นระบบ คาดเดาง่าย และมีความปลอดภัยสูง โดยทั่วไปมักอ้างอิงตามมาตรฐาน RESTful API ซึ่งมีหมวดหมู่สำคัญดังนี้ครับ:
------------------------------
## 1. การตั้งชื่อ URL (Resource-Based Naming)

* ใช้คำนามพหูพจน์: URL ต้องเน้นที่ "ข้อมูล/ทรัพยากร" (Resource) ไม่ใช่การกระทำ (Action) [1]
* ควรใช้: GET /api/v1/customers [1]
   * ไม่ควรใช้: GET /api/v1/getAllCustomers หรือ POST /api/v1/createNewCustomer [1]
* ใช้ตัวพิมพ์เล็กทั้งหมด: แยกคำด้วยเครื่องหมายขีดกลาง (Kebab-case) และห้ามลงท้ายด้วยเครื่องหมายสแลช (/) [1]
* ตัวอย่าง: /api/v1/premium-customers [1]

## 2. การใช้ HTTP Methods ให้ถูกหน้าที่
การกระทำกับข้อมูลจะถูกกำหนดด้วย HTTP Methods แทนการตั้งชื่อบน URL:

* GET: ใช้ดึงข้อมูล (ห้ามทำการแก้ไขข้อมูลในระบบ) [1]
* POST: ใช้สร้างข้อมูลใหม่ [1]
* PUT: ใช้แก้ไขข้อมูลเดิม โดยส่งข้อมูลไปทดแทนทั้งหมด (Replace) [1]
* PATCH: ใช้แก้ไขข้อมูลเดิมเฉพาะบางฟิลด์ (Partial Update) [1]
* DELETE: ใช้ลบข้อมูล [1]

## 3. รูปแบบการส่งข้อมูล (Request & Response Payload)

* JSON Format: ใช้ JSON เป็นสื่อกลางในการรับส่งข้อมูลเป็นหลัก [1]
* Naming Style: นิยมใช้แบบ camelCase สำหรับคีย์ใน JSON Payload [1]
* ตัวอย่าง Request (POST /api/v1/customers):

{
  "firstName": "Somsak",
  "lastName": "Jaidee",
  "email": "somsak@example.com"
}


## 4. การตอบกลับด้วย HTTP Status Codes (Response Conventions)
ต้องส่งรหัสสถานะที่ถูกต้องกลับไปเสมอ เพื่อให้ฝั่งหน้าบ้าน (Client) จัดการต่อได้ง่าย:

* 200 OK: ทำงานสำเร็จและส่งข้อมูลกลับไป (มักใช้กับ GET, PUT, PATCH) [1]
* 201 Created: สร้างข้อมูลใหม่สำเร็จ (มักใช้กับ POST) [1]
* 400 Bad Request: ข้อมูลที่ส่งมาไม่ถูกต้อง (เช่น ลืมใส่ฟิลด์ที่จำเป็น) [1]
* 401 Unauthorized: ไม่ได้เข้าสู่ระบบ หรือ Token หมดอายุ [1]
* 403 Forbidden: เข้าสู่ระบบแล้ว แต่ไม่มีสิทธิ์เข้าถึงข้อมูลนี้ [1]
* 404 Not Found: ไม่พบข้อมูลหรือ URL ที่เรียก [1]
* 500 Internal Server Error: เกิดข้อผิดพลาดที่ฝั่งเซิร์ฟเวอร์ (เช่น ระบบล่ม, Database หลุด) [1]

## 5. มาตรฐานการตอบกลับเมื่อเกิดข้อผิดพลาด (Error Handling Response)
เมื่อ API พังหรือเกิด Error ควรส่งโครงสร้างข้อผิดพลาดที่เป็นรูปแบบเดียวกันทั้งระบบ เพื่อให้หน้าบ้านแกะไปแสดงผลให้ผู้ใช้ดูได้ง่าย:

{
  "success": false,
  "error": {
    "code": "INVALID_EMAIL",
    "message": "รูปแบบอีเมลไม่ถูกต้อง",
    "details": [
      "ฟิลด์ 'email' ต้องระบุเครื่องหมาย @ ให้ถูกต้อง"
    ]
  }
}

## 6. การใส่เวอร์ชัน (API Versioning)

* บังคับใส่เวอร์ชันไว้บน URL เสมอ เพื่อป้องกันไม่ให้ระบบหน้าบ้านพังเมื่อมีการแก้ไขโครงสร้าง API ในอนาคต [1]
* ตัวอย่าง: /api/v1/products [1]
